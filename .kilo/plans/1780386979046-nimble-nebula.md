# Rework Site Scoring And Remove Control Markers

## Confirmed scope

User clarified that `control_marker` logic should be removed everywhere, not only in final scoring. That means scoring, card-effect counting, board creator data, serialized board data, tests, and UI that currently depends on marker state should move to derived control / total-control checks.

## Assumptions

- `CONTROL` means the same majority rule currently implemented by `_site_control_owner()`: count troops on the site, ignore empty slots, require a unique highest troop count, and do not award control to `white`.
- `TOTAL CONTROL` means the current `_is_total_control()` rule: all troop slots on the site are occupied by the same player and there are no enemy spies on that site.
- Route nodes keep their existing fields unless implementation review finds they are also incorrectly carrying board-creator scoring fields that should be site-only.

## Clarification resolved

- Replace marker-based concepts everywhere with derived control checks from live board state.

## Success criteria

1. Board data describes sites with two explicit scoring fields:
   - end-game VP for `CONTROL`
   - per-turn VP for `TOTAL CONTROL`
2. Engine scoring no longer reads or writes `control_marker`.
3. Runtime state no longer needs a `control_marker` field.
4. Card-effect logic that counted `owned_control_markers` uses derived controlled-site counts instead.
5. Board creator prompts, editable node model, and package serialization expose the two site scoring fields clearly.
6. Existing tests are rewritten to validate derived control logic and the new scoring split.
7. Relevant test suite passes.

## Implementation plan

1. Update board schema and runtime state models.
   - In `engine/state.py`, replace `NodeDefinition.vp_value` with two explicit fields for sites:
     - `control_vp` (end-game VP for control)
     - `total_control_vp_per_turn` (per-turn VP for total control)
   - Remove `initial_control_marker` from `NodeDefinition`.
   - Remove `control_marker` from `NodeState`.
   - Keep validation simple and non-speculative:
     - both new fields non-negative
     - route validation unchanged unless route scoring fields become obviously invalid under current loaders/tests
   - Verify by updating model-construction tests / fixture loads so board JSON still validates.

2. Migrate board package load/save and board creator models.
   - In `interface/board_creator.py` and `interface/package_manager.py`:
     - remove `initial_control_marker`
     - rename/replace `vp_value` with `control_vp`
     - rename/replace `vp_income` with `total_control_vp_per_turn`
     - update labels shown in the site metadata dialog to match the user wording
   - Ensure serialized board JSON uses the new field names.
   - Review route metadata separately:
     - if routes do not participate in these scoring rules, do not expose site-only scoring labels for routes
     - if routes still need a generic VP/token/income field for unrelated mechanics, preserve only what is actually used
   - Verify by checking package round-trip tests and board creator package-building tests.

3. Replace marker-based scoring helpers with derived control helpers.
   - In `engine/scoring.py`:
     - remove `sync_site_control_markers()`
     - replace `_site_control_owner()` with a pure helper such as `controlled_site_owner()` or similar that derives control from `troop_slots`
     - keep `_is_total_control()` or rename consistently if useful
     - update `award_end_of_turn_site_vp()` to sum `total_control_vp_per_turn` for sites where player has total control
     - update `compute_final_scores()` to sum `control_vp` for sites where player has control
     - final score should no longer add a flat `+2` per total-control site unless that value is encoded in data
   - Verify with focused scoring tests covering:
     - control with unique majority
     - no control on ties
     - white troops never owning control
     - end-of-turn total-control VP using per-site configured values
     - final scoring using control VP only

4. Remove marker recalculation from rules flow.
   - In `engine/rules.py`, remove all calls to `sync_site_control_markers()` after troop/spy changes and at end of turn.
   - Replace `_count_owned_control_markers()` usage with derived controlled-site counting.
   - For card metadata using `count_from="owned_control_markers"`, either:
     - map it to derived controlled-site count internally, or
     - rename the metadata consumer while keeping backward compatibility for existing card data if the repo still ships that metadata
   - Minimal-change recommendation: keep accepting `owned_control_markers` in card metadata, but interpret it as derived controlled sites so card JSON does not need a simultaneous migration unless required.
   - Verify with existing card-effect tests, especially the `white_dragon` case around `tests/test_rules.py:2518+`.

5. Update UI read models and viewer breakdowns.
   - In `game_view.py`, `interface/game_renderer.py`, and `interface/game_viewer.py`:
     - stop reading `control_marker` from runtime state
     - derive displayed control owner from current site occupancy
     - update VP breakdown labels to reflect `control_vp` and configured per-turn total-control VP instead of hard-coded `+2`
   - Verify by checking view-model tests and any renderer tests that assert owner/border state.

6. Rewrite affected tests surgically.
   - `tests/test_scoring.py`
     - remove assertions about persisted marker state
     - assert derived control owner helper directly
     - add tests for configured `total_control_vp_per_turn`
   - `tests/test_rules.py`
     - replace `test_deploy_places_troop_and_updates_control_marker` with a deploy test that verifies board occupancy only, or derived control if needed
     - replace marker setup in effect-scaling tests with troop-slot setups that imply control
   - `tests/test_board_package.py`, `tests/test_board_view.py`, `tests/test_generic_interpreter.py`, and any fixture builders
     - swap old field names for new ones
     - remove `initial_control_marker`
   - Verify by running targeted pytest files first, then the full suite.

7. Data migration for shipped board JSON.
   - Update `data/boards/*.json` field names:
     - `vp_value` -> `control_vp` for site end-game control scoring
     - `vp_income` -> `total_control_vp_per_turn` for site end-of-turn total-control scoring
     - remove `initial_control_marker`
   - Review whether route nodes currently store these fields and whether they should remain zero-valued, be renamed, or be removed from route records.
   - Verify by loading both shipped boards through the existing loader entry points.

## Risks and decisions to watch during implementation

- `owned_control_markers` is referenced by card logic. Removing markers from runtime state without remapping this count source would silently break card effects.
- Some UI tests may assume marker persistence rather than derived ownership and will need behavioral, not mechanical, updates.
- The board creator already has a `vp_income` site field labeled `VP/turn (total control)`, so part of the requested change is a naming/schema cleanup, not a brand-new feature.
- If route nodes currently carry `vp_value` / `vp_income` in saved data, implementation should verify whether those fields are genuinely used before removing them from route serialization.
