# Engine Simulation Performance Plan

## Goal

Make simulated game runs materially faster without changing game outcomes, move legality, or determinism.

## What The Code Inspection Shows

1. The current simulation loop pays for full view construction on every step, not just engine work.

   `game_simulation.py:95-133` calls `build_game_view(session)` every iteration before choosing a move.

   `game_view.py:175-258` then rebuilds a full `GameView` from `session.snapshot()`, including:
   - full legal move projection
   - labels via `describe_move(...)`
   - `move.model_dump(mode="json")` for every legal move
   - card, board, prompt, and summary view objects

   This is outside `engine/`, but it directly slows simulated runs.

2. The engine still spends a lot of time deep-copying whole state trees.

   `engine/state.py:371-405` defines a custom `GameState.__deepcopy__` that already avoids copying immutable definitions, which is a good optimization, but the engine still calls `state.model_copy(deep=True)` very frequently.

   High-frequency examples:
   - `engine/rules.py:306-309`
   - `engine/rules.py:386-415`
   - `engine/rules.py:592-605`
   - `engine/rules.py:614-625`
   - `engine/rules.py:637-656`
   - `engine/rules.py:703-711`
   - `engine/rules.py:717-718`
   - `engine/phases.py:22-43`
   - `engine/scoring.py:48-60`

   More importantly, several generic action handlers deep-copy repeatedly inside loops:
   - `engine/rules.py:2510-2532`
   - `engine/rules.py:2570-2598`
   - `engine/rules.py:2618-2633`
   - `engine/rules.py:2649-2761`
   - `engine/rules.py:2880-2985`
   - `engine/rules.py:3030-3110`

3. Immutable lookup maps are rebuilt over and over.

   `engine/state.py:414-423` rebuilds dictionaries every time `board_index(...)` or `card_index(...)` is called.

   Those helpers are used heavily across hot paths, including:
   - `engine/rules.py:71, 80, 229, 520, 1484, 1798, 1810, 1850, 2744`
   - `engine/scoring.py:49, 66-67`
   - `game_view.py:185, 264`

   Because board and card definitions are immutable, these lookups should be cached once.

4. Legal-move generation repeatedly rescans the board and recomputes presence.

   `engine/rules.py:517-562` builds main-phase moves by scanning deploy targets, assassinate targets, and recruit targets.

   `engine/rules.py:572-583` calls `_player_has_any_troops_on_board(...)` and `has_presence(...)` from `_can_deploy_to_node(...)`, causing repeated board scans.

   `engine/rules.py:565-569` scans the whole board to answer whether the player has any troops.

   `engine/rules.py:226-242` recomputes adjacency-based presence checks repeatedly.

5. The largest complexity hotspot is also likely a runtime hotspot.

   `engine/rules.py:1476-1935` (`_legal_generic_target_selection_moves`) is the biggest move-generation function in the engine. It:
   - branches over many action types
   - repeatedly sorts node ids
   - repeatedly scans board state
   - creates many `ResolveGenericChoiceMove` objects

   `repowise_get_health` also flags it as the dominant brain method in `engine/rules.py`.

## Recommended Optimization Order

### P0: Add a Repeatable Benchmark First

Create a small benchmark harness before changing behavior.

Scope:
- engine-only benchmark: loop on `engine.rules.legal_moves(state)` + `engine.rules.apply(state, move)`
- full simulation benchmark: current `run_simulation(...)`
- at least one fixed 2-player seed and one fixed 4-player seed
- capture:
  - steps/sec
  - total time for 1,000 or 5,000 steps
  - top cumulative functions from `cProfile`

Success criteria:
- there is a stable baseline before and after each optimization pass
- fast-path improvements are measured separately from engine-only improvements

Implementation note:
- use the project interpreter from `justfile` (`.venv/Scripts/python.exe`)
- keep this benchmark out of normal test runtime; make it an opt-in script or perf-marked test

### P1: Split Simulation Speed From UI/View Speed

Add a dedicated fast simulation path that does not build a `GameView` every turn.

Why:
- for Monte Carlo or bulk random runs, the engine only needs legal moves and state transitions
- `GameView` projection is valuable for replay/UI, but it is not required for pure throughput

Plan:
- keep existing `run_simulation(...)` behavior for replay-rich workflows
- add a fast alternative, e.g. `run_fast_simulation(...)`, that:
  - pulls moves directly from `legal_moves(session.state)` or directly from a local `state`
  - applies moves directly with `apply(...)`
  - records only minimal replay data when requested
- if full replay output is needed, optionally reconstruct views later from the move log rather than during the run

Expected impact:
- likely the largest wall-clock gain for simulated runs overall

Validation:
- same seed and chooser should produce the same move sequence and winner as the current path

### P2: Cache Immutable Definition Lookups

Remove repeated rebuilding of definition-derived maps.

Targets:
- `board_index(...)` in `engine/state.py:414-418`
- `card_index(...)` in `engine/state.py:420-423`

Plan:
- cache these once per immutable definition object
- safe options:
  - cached private attrs on the definition models
  - module-level cache keyed by object identity
  - precomputed lookup fields created during setup

Also precompute other cheap immutable helpers while there:
- site node ids
- route node ids
- board adjacency lookup in ready-to-use form
- card cost/aspect lookup tables if profiler confirms value

Expected impact:
- small-to-medium per call
- large cumulative savings because these helpers are used in rules, scoring, and view building

Validation:
- equality tests before/after for representative states
- benchmark should show reduced time in `board_index` / `card_index` callers

### P3: Replace Whole-State Deep Copies In The Hot Path

This is the highest-value engine-only change.

Why:
- the engine copies the entire runtime state even when a move only touches one player, one node, one resource pool, or one pending-choice object
- some generic handlers deep-copy once per repeated action iteration

Plan:
- introduce targeted copy helpers for the mutable runtime tree
- copy only the branches being mutated:
  - `players[player_id]`
  - affected `NodeState`
  - `resource_pool`
  - `market`
  - pending-choice / promotion structures
- keep immutable `definition` shared exactly as today

Good first targets:
- `engine/rules.py:660-688` `_apply_deploy`
- `engine/rules.py:691-731` `_apply_recruit`
- `engine/rules.py:376-419` `_apply_play_card`
- `engine/rules.py:1128-1144` `_apply_cleanup`
- `engine/phases.py:19-55`
- `engine/scoring.py:45-60`

Then clean up looped copy patterns in generic handlers:
- `engine/rules.py:2493-2761`
- `engine/rules.py:2848-3115`

Implementation strategy:
- do this incrementally, not as one giant rewrite
- start with the most common moves in random simulations: play, deploy, recruit, end turn, cleanup
- only move to generic-card handlers after the benchmark proves where time still goes

Validation:
- existing engine tests
- deterministic random-walk comparison before/after
- explicit no-mutation tests for the original input state on representative moves

### P4: Flatten Legal Move Generation

Optimize `legal_moves(...)` so it computes shared facts once per call instead of many times.

Targets:
- `engine/rules.py:245-284` `legal_moves`
- `engine/rules.py:517-562` `_legal_main_phase_actions`
- `engine/rules.py:1476-1935` `_legal_generic_target_selection_moves`

Plan:
- compute shared per-call facts once:
  - whether the player has any troops on board
  - nodes where the player has presence
  - empty slots by node
  - enemy troop slots by node
  - spy locations by node
  - affordable market slots
- pass that precomputed context into helper functions instead of recomputing it inside nested loops
- preserve deterministic ordering, but stop re-sorting if definition order is already stable and sufficient

Specific fixes worth doing early:
- avoid calling `_player_has_any_troops_on_board(...)` inside every `_can_deploy_to_node(...)` check
- avoid repeated `has_presence(...)` recomputation during assassinate and generic-target scans
- avoid repeated `board_index(...)` lookup inside inner loops

Structural refactor:
- split `_legal_generic_target_selection_moves(...)` into per-op helpers behind a dispatch table
- keep behavior identical, but make each op-specific selector easier to profile and optimize

Expected impact:
- medium-to-large, especially in simulations with many generic card effects

Validation:
- exact legal move sets must remain identical for fixed snapshots
- add focused tests for representative pending generic choice states

### P5: Reduce Object Construction Overhead If Needed

Only do this after P1-P4 are measured.

Possible targets:
- large numbers of Pydantic `Move` instances in legal move generation
- `move.model_dump(mode="json")` in `game_view.py:226-233`
- repeated `CardView`/`LegalMoveView`/prompt creation during simulations

Options:
- keep Pydantic validation only at I/O boundaries
- use lighter internal move objects or slot-based dataclasses for engine-internal enumeration
- delay JSON payload construction until a caller explicitly requests it

This is a second-pass optimization because it is more invasive than caching and copy reduction.

## Suggested Execution Sequence

1. Add benchmark harness and collect baseline.
2. Add fast simulation path that skips `GameView` construction.
3. Cache `board_index(...)` / `card_index(...)` and related immutable lookups.
4. Optimize common move application paths to stop copying the whole state tree.
5. Refactor and optimize legal-move generation, especially generic target selection.
6. Re-profile.
7. Only then decide whether move-model/object-allocation changes are necessary.

## Validation Plan

After each phase:
- run `pytest`
- compare deterministic simulations before/after on fixed seeds
- compare:
  - step count
  - winner
  - final scores
  - serialized move payloads when using the replay-preserving path

For the new fast path:
- ensure equivalence with the existing path on the same chooser and seed
- allow the replay-rich path to remain the compatibility path

## Recommended Success Metrics

Use relative improvement targets rather than guessing absolute times.

Targets:
- full simulated run throughput: at least 2x faster
- engine-only throughput: at least 1.5x faster
- no behavioral regressions in deterministic simulation output

## Lowest-Risk First Changes

If the goal is quickest payoff with minimal engine risk, start here:

1. Fast simulation path without `GameView`
2. Cached `board_index(...)` and `card_index(...)`
3. `_legal_main_phase_actions(...)` shared-context optimization
4. Replace whole-state copies in `_apply_deploy`, `_apply_recruit`, `_apply_cleanup`, and phase transitions

That sequence should deliver most of the practical speedup before touching the most complex generic-card machinery.
