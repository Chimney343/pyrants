# `engine/rules.py` readability review and refactor plan

## Review verdict

`engine/rules.py` needs structural refactoring, not just formatting.

The file is currently hard to read because it mixes too many responsibilities in one place and hides major rules behind very large `if` ladders. Ruff formatting alone will not fix the real problem.

## Verified findings

- `engine/rules.py` is 3017 lines long and contains 84 top-level definitions. It currently mixes public rules API, board-action rules, phase handling, generic-card execution state machine, selection generation, effect registry, and concrete effect handlers in one file.
- `legal_moves()` at `engine/rules.py:234` and `apply()` at `engine/rules.py:276` are readable enough on their own, but the helpers they depend on are interleaved with unrelated generic-runtime code, so understanding one path requires jumping across hundreds of lines.
- `_legal_generic_target_selection_moves()` at `engine/rules.py:1465` through `engine/rules.py:1923` is the biggest readability problem. It branches on many `action.op` values and also nests `custom_effect` subcases inside the same function. This hides the selection rules for deploy, assassinate, supplant, return, promote, play, devour, and custom effects in one 450-line block.
- `_apply_generic_action()` at `engine/rules.py:2149` through `engine/rules.py:2938` is another major hotspot. It is one long operation dispatcher with repeated validate/copy/mutate/sync patterns. Even when behavior is correct, it is difficult to scan because every operation follows its own mini-protocol.
- Several smaller helpers repeat normalization logic instead of centralizing it:
- `_scaled_vp_award_count()` at `engine/rules.py:112` through `engine/rules.py:170`
- `_action_requires_selection()` at `engine/rules.py:1304` through `engine/rules.py:1340`
- the `conditional_bonus` block inside `_apply_generic_action()` at `engine/rules.py:2615` through `engine/rules.py:2747`
- the `custom_effect` block inside `_apply_generic_action()` at `engine/rules.py:2749` through `engine/rules.py:2863`
- The generic runtime relies on raw `selection: dict[str, object]` payloads passed between move generation and move application. That contract is spread across many branches and repeated via magic string keys like `target_node_id`, `target_slot_index`, `source_zone`, `market_slot`, and `target_player_id`.
- Mutation boundaries are noisy. The file repeats `model_copy(deep=True)`, `board_index(...)`, and `sync_site_control_markers(...)` many times, which makes it harder to see which branches only validate and which branches actually transition state.
- `_legal_main_phase_actions()` at `engine/rules.py:506` through `engine/rules.py:551` is much smaller, but it still mixes three distinct concerns: deploy generation, assassinate generation, and recruit generation. It is a good candidate for a cleanup pass once the bigger hotspots are split.

## Refactor goals

- Preserve behavior of `legal_moves()`, `apply()`, move models, and card data contracts.
- Make related rules live together so a reader can follow one rules path without jumping through the whole file.
- Replace giant `if` ladders with small dispatch helpers grouped by operation family.
- Prefer one clear subsystem extraction over many tiny files.
- Keep the refactor mostly mechanical and test-backed. No gameplay changes should be introduced as part of the readability pass.

## Recommended implementation plan

1. Lock down current behavior with focused tests.

Add or tighten tests around the generic runtime paths most likely to regress during extraction. The highest-value coverage is in `tests/test_generic_interpreter.py` and `tests/test_rules.py`.

Target these flows explicitly:
- target-selection generation for `deploy_troops`, `assassinate_troop`, `supplant_troop`, `return_spy`, `return_unit`, `move_troop`, `promote_card`, `play_card`, and `devour_cost`
- option handling for modal and repeat generic choices
- `custom_effect` branches that require player selections
- `conditional_bonus` branches that depend on last selection or focus
- nested `play_card` behavior that preserves the outer pending generic choice
- end-of-turn generic effects, especially `force_discard` and scaled VP timing

2. Add a small readability layer before moving code.

Still inside `engine/rules.py`, introduce only a few helpers that reduce repetition without creating new abstraction sprawl.

Recommended helpers:
- metadata normalization helpers for common integer/resource parsing
- a tiny helper for repeated "grant resource" behavior
- a tiny helper for repeated state-copy-plus-control-sync behavior where troop changes happen
- section headers or short comments separating public API, core board actions, generic runtime, and effect registration

This step should stay small. The goal is to remove noise before extracting larger pieces.

3. Split generic target selection into per-op helpers.

Refactor `_legal_generic_target_selection_moves()` into a thin dispatcher plus small helpers, for example:
- `_legal_generic_deploy_targets(...)`
- `_legal_generic_assassinate_targets(...)`
- `_legal_generic_supplant_targets(...)`
- `_legal_generic_place_spy_targets(...)`
- `_legal_generic_return_spy_targets(...)`
- `_legal_generic_return_unit_targets(...)`
- `_legal_generic_move_troop_targets(...)`
- `_legal_generic_force_discard_targets(...)`
- `_legal_generic_promote_targets(...)`
- `_legal_generic_recruit_targets(...)`
- `_legal_generic_play_targets(...)`
- `_legal_generic_devour_targets(...)`
- `_legal_generic_custom_effect_targets(...)`

Within `custom_effect`, split again by `effect_kind` when needed. The important change is that each helper should express one target-selection rule family only.

4. Split generic action application into per-op handlers.

Refactor `_apply_generic_action()` into a thin dispatcher plus small per-op handlers. Keep the existing function name as the stable entry point, but make it route to helpers.

Suggested handler families:
- resource and card economy: gain resource, draw cards, grant VP, recruit card
- troop and spy board manipulation: deploy, assassinate, supplant, place spy, return spy, return unit, move troop
- card-zone manipulation: devour, promote, nested play-card
- metadata-driven branches: conditional bonus, custom effect

Do not introduce a large class hierarchy for this. Small private helper functions are enough.

5. Extract the generic-card runtime into one new private module.

After steps 3 and 4, move the generic interpreter subsystem out of `engine/rules.py` into a single sibling module such as `engine/generic_runtime.py`.

Recommended extraction boundary:
- `_resolve_action_count()`
- `_resolve_runtime_action_count()`
- `_pending_action_counter_key()`
- `_pending_action_counter_value()`
- `_action_requires_additional_choice()`
- `_resolve_card_option_actions()`
- `_action_requires_selection()`
- `_action_focus_requirement_met()`
- `_pending_generic_card_definition()`
- `_pending_generic_active_action()`
- `_available_repeat_option_ids()`
- `_generic_choice_move()`
- `_option_is_currently_selectable()`
- `_legal_pending_generic_choice_moves()`
- the new per-op target-selection helpers from step 3
- `_apply_resolve_generic_choice()`
- `_auto_resolve_pending_generic()`
- `_require_selection_string()`
- `_require_selection_int()`
- the new per-op action handlers from step 4
- `_resolve_generic_execution()`

Keep `rules.py` as the public entry point for the engine. It should still expose `legal_moves()` and `apply()`, but the generic-card subsystem should live behind a narrow private import.

This is the step most likely to make `rules.py` feel readable again.

6. Do a final pass on smaller core helpers.

Once the generic runtime is gone, clean up the remaining file:
- split `_legal_main_phase_actions()` into small generators for deploy, assassinate, and recruit moves
- simplify `_scaled_vp_award_count()` by normalizing `count_from` and `per` early
- group closely related board-action helpers together
- keep docstrings on public functions and add short comments only where control flow is genuinely tricky

## Constraints for the implementation

- Do not change public behavior intentionally.
- Do not rewrite state models or move models as part of this pass.
- Do not introduce multiple new modules. One extracted generic-runtime module is enough.
- Do not replace raw selection dicts with a large new type system in the same refactor. That is a separate design change and would expand scope too much.

## Risk hotspots to protect during refactor

- pending generic choice advancement order
- repeat-choice bookkeeping via `remaining_repeats` and `selected_option_ids`
- action counter bookkeeping for repeated actions like deploy and assassinate
- `last_selection` propagation between sequential generic actions
- nested `play_card` preserving the outer pending choice and rejecting nested unresolved prompts
- end-of-turn ordering between promotions, generic effects, site VP, and cleanup
- troop-changing actions that must call `sync_site_control_markers(...)`

## Validation plan

Run these checks after implementation:
- `ruff check .`
- `pytest tests/test_rules.py tests/test_generic_interpreter.py tests/test_state_machine.py tests/test_scenarios.py`
- `pytest`

## Expected outcome

After this refactor, `engine/rules.py` should primarily read as the public rules surface plus core turn/board rules, while the generic card interpreter lives in one focused private module. That gives a reader a much shorter path to understand ordinary move legality and application, and it isolates the data-driven generic runtime where its complexity belongs.
