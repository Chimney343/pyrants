# MCTS Implementation Plan for Tyrants of the Underdark

## Goal

Implement a Monte Carlo Tree Search agent that can play the game through the existing pure-function engine API (`engine.rules.legal_moves`, `engine.rules.apply`, `engine.rules.is_terminal`, `engine.rules.winner`).

## Architecture Summary

**Work on the fast engine path only.** The engine already provides:

- `legal_moves(state) -> list[Move]` — generates all legal moves for current phase/player
- `apply(state, move) -> GameState` — pure transition, returns new immutable state (shares frozen `GameDefinition`)
- `is_terminal(state) -> bool` — checks market deck empty or any barracks=0
- `winner(state) -> str | None` — returns winner player_id or None for tie
- `compute_final_scores(state) -> dict[str, int]` — final VP tally
- `GameState.__deepcopy__` — optimized deep copy that shares the immutable definition tree (~10ms saved per copy vs naive)

The MCTS module lives entirely in `engine/mcts.py` with a thin CLI entry point in `scripts/mcts_play.py`.

## Phase 1: Core MCTS Engine (`engine/mcts.py`)

### 1.1 Node class

```python
@dataclass
class MCTSNode:
    state: GameState           # root stores full state; children store None (reconstructed on demand) or full state
    parent: MCTSNode | None
    move: Move | None          # the move that led to this node
    children: list[MCTSNode]   # expanded children
    untried_moves: list[Move]  # moves not yet expanded
    visits: int = 0
    rewards: dict[str, float] = field(default_factory=dict)  # per-player cumulative reward
```

- **Root node** holds the full `GameState`.
- **Child nodes** store only the `Move` that produced them. The child's state is lazily reconstructed via `apply(parent.state, move)` and cached. This avoids materializing all child states upfront.

### 1.2 Selection policy — UCB1

```python
def ucb1(node: MCTSNode, player_id: str, exploration: float = 1.414) -> float:
    if node.visits == 0:
        return float("inf")
    return node.rewards.get(player_id, 0.0) / node.visits + exploration * sqrt(log(node.parent.visits) / node.visits)
```

Selection walks from root, picking the child with highest UCB1 score for the **current player at that node** (i.e., the player whose turn it is in the child's state). This is critical: the tree alternates players, so the UCB1 perspective switches at each level. Under max^n, each player greedily selects the action that maximizes their own accumulated reward.

### 1.3 Expansion

Pop one move from `untried_moves`, apply it to the parent state, create a child node with the resulting state's legal moves as its `untried_moves`.

For multi-action turns (a player plays multiple cards/deploys/assassinates before ending main phase), the tree naturally handles this because each action is a separate `Move` producing a separate state.

### 1.4 Rollout (Simulation)

Use the existing `EngineMoveChooser` interface from `game_simulation.py`:

```python
from game_simulation import EngineMoveChooser, make_random_legal_move_chooser_engine
```

The rollout policy starts as **uniform random** (pick a random legal move). This can be upgraded later with heuristics (prioritize deploys when power > 0, assassinate when possible, recruit high-value cards).

Rollout runs until `is_terminal(state)` returns True. A safety cap of 1000 steps prevents infinite loops in edge cases.

### 1.5 Reward computation

At terminal state, use `compute_final_scores(state)`:

```python
def terminal_reward(state: GameState, player_ids: list[str]) -> dict[str, float]:
    scores = compute_final_scores(state)
    max_score = max(scores.values())
    return {
        pid: 1.0 if scores[pid] == max_score and list(scores.values()).count(max_score) == 1
        else (0.5 if scores[pid] == max_score else 0.0)
        for pid in player_ids
    }
```

- **Win**: 1.0
- **Tie**: 0.5
- **Loss**: 0.0

For non-terminal states reaching max depth, use a **heuristic evaluation** (Phase 3).

### 1.6 Backpropagation

Walk up from the expanded node to root, incrementing `visits` and accumulating `rewards[player_id]` for each player based on the rollout result.

Under **max^n**, every node stores per-player reward totals. When selecting during UCB1, the selecting player uses only their own reward component. This is the standard multiplayer MCTS approach and avoids the pessimism of the "paranoid" model where opponents collude against the searcher.

### 1.7 Search function

```python
def mcts_search(
    state: GameState,
    *,
    iterations: int = 1000,
    exploration: float = 1.414,
    rollout_policy: EngineMoveChooser | None = None,
    safety_cap: int = 1000,
) -> Move:
```

Returns the best move (most visited child of root).

## Phase 2: CLI Integration (`scripts/mcts_play.py`)

A script that:

1. Loads a game from scenario or standard files (reuse `GameSession.from_files` / `load_game_state_from_scenario`)
2. Creates an MCTS agent for the searching player
3. Runs `mcts_search` with configurable budget
4. Prints the chosen move and updated state
5. Optional: run full game (MCTS vs random, MCTS vs MCTS) and report outcome

```bash
python scripts/mcts_play.py --iterations 1000 --seed 42 --players p1,p2,p3,p4 --search-player p1
```

## Phase 3: Heuristic Evaluation (Safety Net)

Rollouts run to completion, but a safety cap of 1000 steps prevents infinite loops. If the safety cap is hit, use a fast heuristic score instead of the random 0/1 reward. Based on `compute_final_scores`:

```python
def heuristic_reward(state: GameState, player_ids: list[str]) -> dict[str, float]:
    scores: dict[str, float] = {}
    for pid in player_ids:
        player = state.players[pid]
        s = player.score  # accumulated VP so far
        # Approximate end-game VP without full computation:
        s += len(player.trophy_hall)  # 1 VP per trophy
        s += player.vp_tokens
        # Don't count deck_vp / inner_circle_vp (expensive)
        scores[pid] = float(s)

    total = sum(scores.values())
    if total == 0:
        return {pid: 0.25 for pid in player_ids}  # uniform
    return {pid: scores[pid] / total for pid in player_ids}
```

This gives a soft signal keyed to current board position strength, normalized to [0, 1].

## Phase 4: Rollout Policy Improvements

The default random rollout is weak. Priority upgrades:

1. **Weighted random**: Bias toward deploy/assassinate/recruit over end_main_phase when the player has resources.
2. **Greedy card play**: Play the highest-impact card first (use a simple heuristic: prefer cards that give power+influence, or cards with deck_vp > 0).
3. **End-phase awareness**: If no more useful actions, prefer end_main_phase rather than random delay.

These go into `engine/mcts_policies.py` and are pluggable via the `rollout_policy` parameter.

## Phase 5: Performance Optimizations

### 5.1 State reuse and lazy expansion

Only store `GameState` at the root and on demand. Children reconstruct state lazily:

```python
class LazyMCTSNode:
    parent_state: GameState | None  # cached
    move: Move                     # edge label
    _state: GameState | None = None

    @property
    def state(self) -> GameState:
        if self._state is None:
            self._state = apply(self.parent.state, self.move)
        return self._state
```

Trade-off: caching states uses more memory; recomputing uses more CPU. Make it configurable.

### 5.2 Move grouping (optional)

Group similar moves (e.g., all deploy moves to empty sites with presence) to reduce branching factor during selection. Expand them individually during rollout.

### 5.3 Parallel rollouts (optional, later)

Use `multiprocessing.Pool` or `concurrent.futures.ProcessPoolExecutor` to parallelize rollouts. Each worker copies the root state and runs independent rollouts, sharing the tree via a lock.

### 5.4 Benchmarking

Extend `scripts/bench_simulation.py` with an MCTS benchmark:

```python
def bench_mcts(iterations=1000) -> float:
    state = load_game_state_from_scenario(SCENARIO_2P)
    t0 = time.perf_counter()
    best_move = mcts_search(state, iterations=iterations)
    elapsed = time.perf_counter() - t0
    return elapsed
```

Target: < 5 seconds for 1000 iterations on a 2-player midgame state.

## Confirmed Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Perfect vs hidden info | Open-loop with determinization (future) | Start simple (perfect info), add IS-MCTS later |
| Transposition table | No (V1) | State space too large for meaningful reuse; saves complexity |
| Opponent model | **Max^n** | Each player maximizes their own reward. Standard multiplayer MCTS. Most accurate model. |
| Reward mapping | Win=1, Tie=0.5, Loss=0 | Works with max^n; each player tracks own cumulative reward |
| Move selection | Most visited child | Robustness over exploitability (most-visited ≈ best under UCT) |
| State storage | Lazy/cached at root, on-demand for children | Avoids materializing the full tree's worth of states |
| Rollout policy | Random legal (V1), pluggable | Can upgrade independently of tree logic |
| Rollout depth | **Run to completion** (no cap) | More accurate terminal evaluation; depth cap removed per user preference |
| Budget type | **Iteration count** (e.g., 1000) | Deterministic, reproducible, easy to benchmark |
| Interruptible | **No (V1)** | Simple blocking call; add interruptibility later if needed for GUI |
| Parallelism | None (V1) | Single-threaded first; add parallel rollouts as optimization |
| Engine path | Fast path only (`engine.rules.*`) | Bypasses `GameSession`/`GameView` overhead (~3-5x speedup per bench) |

## Implementation Order

1. **Phase 1** — Core MCTS (`engine/mcts.py`): MCTSNode, UCB1, selection, expansion, rollout, backprop, mcts_search
2. **Phase 2** — CLI script (`scripts/mcts_play.py`)
3. **Phase 3** — Heuristic evaluation for non-terminal rollouts
4. **Phase 6** — Tests (can be written in parallel with Phase 1)
5. **Phase 4** — Smarter rollout policies
6. **Phase 5** — Performance optimizations (lazy nodes, benchmarking, parallelism)

Phases 1-3 and 6 are the MVP. Phases 4-5 are enhancements.
