# Complexity Demon Plan

## Goal
Refactor the biggest complexity hotspots with small, safe steps that preserve behavior and improve maintainability.

## Constraints
- Keep engine pure and preserve existing move/rule behavior.
- Prefer small refactors over architecture rewrites.
- Do not introduce new abstraction layers until a concrete pattern is already visible.
- Keep UI behavior unchanged while reducing class and method size.
- Add or update tests before and during risky engine refactors.

## Findings Summary
1. `engine/rules.py` is the primary hotspot.
   - File is 3265 lines.
   - `_apply_generic_action` is the worst method: ~680 lines, CCN 235, nesting 6.
   - `_legal_generic_target_selection_moves` is ~423 lines, CCN 119, nesting 6.
   - Several helper functions in the same file are also long and branch-heavy.
2. `interface/board_creator.py` contains a God class.
   - `BoardCreatorApp` owns too many responsibilities.
   - `_build_ui` is large, and event handlers mix mode routing, editing behavior, and persistence concerns.
3. `interface/game_viewer.py` contains another God class.
   - `GameViewerApp` owns setup, session orchestration, rendering coordination, layout logic, and UI wiring.
   - `_build_ui`, `_refresh_view`, and `_draw_card_row` are key hotspots.
4. `engine/state.py` is central and relatively stable, but it is an untested hotspot and should be protected by tests when touched indirectly.

## Strategy
Work in three phases:
1. Stabilize with focused tests around current behavior.
2. Refactor `engine/rules.py` in small slices around natural cut points.
3. Refactor UI God classes by extracting cohesive helpers/components without changing behavior.

## Phase 1: Stabilize With Tests

### 1.1 Add characterization coverage for generic rule flows
Target tests at the two most dangerous rule hotspots:
- `engine.rules._legal_generic_target_selection_moves`
- `engine.rules._apply_generic_action`

Add scenario-focused tests that exercise representative branches instead of trying to unit test every internal helper directly.

Recommended test clusters:
- Generic target selection for:
  - `deploy_troops`
  - `assassinate_troop`
  - `place_spy`
  - `return_spy`
  - `return_unit`
  - `promote_card`
  - `recruit_card`
  - `play_card`
  - `devour`
- Generic action application for:
  - conditional bonus resource grants
  - promote from played/hand/discard
  - custom effect branches with player selection and board placement
  - return troop vs return spy
  - play-card effects from market/inner-circle cases

Testing style:
- Prefer integration-style engine tests using public move application where possible.
- Add targeted lower-level tests only where public setup is too expensive.
- Assert exact legal move payloads for a few carefully built states.
- Add regression tests before each risky extraction.

### 1.2 Add smoke protection for UI hotspots
Add minimal non-interactive tests for pure or near-pure UI helpers where practical:
- formatting helpers in `interface/game_viewer.py`
- map/deck profile loading helpers
- any extracted helper functions created during refactor

Avoid deep Tk widget tests unless already common in repo.

## Phase 2: Refactor `engine/rules.py`

### 2.1 Refactor `_legal_generic_target_selection_moves` first
This function has a clear natural split by `action.op`.

Plan:
1. Keep the top-level dispatcher function name unchanged.
2. Extract one helper per operation branch.
3. Keep signatures explicit and local, even if a little repetitive.
4. Do not introduce registry/factory machinery here.

Recommended helpers:
- `_legal_generic_deploy_troops_selection_moves(...)`
- `_legal_generic_assassinate_or_supplant_selection_moves(...)`
- `_legal_generic_custom_effect_selection_moves(...)`
- `_legal_generic_place_spy_selection_moves(...)`
- `_legal_generic_return_spy_selection_moves(...)`
- `_legal_generic_return_unit_selection_moves(...)`
- `_legal_generic_move_troop_selection_moves(...)`
- `_legal_generic_force_discard_selection_moves(...)`
- `_legal_generic_promote_card_selection_moves(...)`
- `_legal_generic_recruit_card_selection_moves(...)`
- `_legal_generic_play_card_selection_moves(...)`
- `_legal_generic_devour_selection_moves(...)`

Implementation notes:
- Inline the nested `_append_for_zone` into a dedicated devour helper instead of keeping nested local functions.
- Pass only the data each helper needs. Do not create a context object unless repeated need emerges after several extractions.
- Keep branch order and behavior identical.

Stop point:
- Run targeted engine tests after this extraction before touching `_apply_generic_action`.

### 2.2 Refactor `_apply_generic_action` second
This is the most complex method and should be reduced to a thin dispatcher.

Plan:
1. Identify each operation handled in the function.
2. Extract one helper per `action.op` branch.
3. Keep top-level `_apply_generic_action(...)` as explicit dispatch.
4. Reuse extracted helpers only when the code is actually identical.

Recommended helper families:
- `_apply_generic_deploy_troops(...)`
- `_apply_generic_assassinate_troop(...)`
- `_apply_generic_supplant_troop(...)`
- `_apply_generic_custom_effect(...)`
- `_apply_generic_conditional_bonus(...)`
- `_apply_generic_return_spy(...)`
- `_apply_generic_return_unit(...)`
- `_apply_generic_move_troop(...)`
- `_apply_generic_force_discard(...)`
- `_apply_generic_promote_card(...)`
- `_apply_generic_recruit_card(...)`
- `_apply_generic_play_card(...)`
- `_apply_generic_devour(...)`

Implementation notes:
- Keep function names boring and obvious.
- Avoid a handler registry unless the code naturally becomes data-driven after extraction.
- Preserve current exceptions and error messages where possible.

### 2.3 Remove obvious copy-paste with tiny helpers
After extraction, remove only duplication that is clearly identical.

Safe candidates:
- resource grant helper for power/influence mutations
- repeated selection object assembly where exact structure repeats
- repeated card lookup/validation snippets only if reused in 3+ places

Do not abstract away every repeated 4-line block. Prefer mild duplication over a clever generic helper.

### 2.4 Reassess state copying after structural cleanup
Do not optimize `state.model_copy(deep=True)` usage first.

Plan:
1. Finish structural refactor first.
2. Add profiling or concrete evidence if deep copy cost matters.
3. Only then consider narrower copy strategies.

This is important because changing copy semantics is higher risk than splitting functions.

### 2.5 Optional file split after behavior is safer
Only after helper extraction and passing tests, consider splitting `engine/rules.py` into submodules by concern.

Possible split:
- `engine/rules_core.py` for public dispatch and main-phase entrypoints
- `engine/rules_generic_selection.py` for legal generic target selection
- `engine/rules_generic_apply.py` for generic action application
- `engine/rules_effects.py` for effect wrappers and effect registry

This split is optional. If extracted helpers inside one file already reduce pain enough, stop there.

## Phase 3: Refactor `interface/board_creator.py`

### 3.1 Split `_build_ui` into section builders
Low-risk first step.

Extract methods such as:
- `_build_menu_bar()`
- `_build_toolbar()`
- `_build_canvas_area()`
- `_build_status_bar()`
- `_bind_events()`

Rules:
- Each helper should mutate `self` and return nothing.
- Keep widget ownership on `self` for compatibility.
- Do not introduce a UI framework layer.

### 3.2 Extract mode-specific canvas behavior
Current editor modes are a natural cut point.

Extract explicit router helpers from event handlers:
- `_handle_select_press/drag/release(...)`
- `_handle_add_site_click(...)`
- `_handle_add_route_click(...)`
- `_handle_connect_click(...)`
- `_handle_resize_press/drag/release(...)`

Then keep top-level event handlers as small mode dispatchers.

Why this cut is good:
- modes are already explicit in `EditorMode`
- behavior groups naturally by user intent
- easier to test and reason about than giant event handlers

### 3.3 Separate node editing workflows from canvas plumbing
Likely extraction targets:
- site metadata prompting/validation
- route metadata prompting/validation
- node creation/update helpers
- save/load path handling and package validation

Candidate helper classes only if needed after extractions:
- `NodeEditService`
- `BoardCreatorPersistence`

Use helper classes only if plain private methods still leave `BoardCreatorApp` too large after step 3.1 and 3.2.

### 3.4 Keep history/background/renderer composed, not expanded
The file already composes:
- `BackgroundImageManager`
- `BoardPackageManager`
- `EditorStateHistory`
- `BoardRenderer`

Preserve this direction. Prefer moving more behavior into focused collaborators instead of adding inheritance or callback-heavy abstractions.

## Phase 4: Refactor `interface/game_viewer.py`

### 4.1 Split `_build_ui` into obvious layout sections
Extract:
- `_build_top_controls()`
- `_build_board_panel()`
- `_build_market_panel()`
- `_build_player_panel()`
- `_build_status_panel()`
- `_bind_events()`

Keep it simple: builder methods populate `self` fields.

### 4.2 Tame `_refresh_view`
Split refresh into explicit stages:
- `_refresh_header_state()`
- `_refresh_board_canvas()`
- `_refresh_market_view()`
- `_refresh_current_player_view()`
- `_refresh_status_and_move_state()`

This keeps redraw order explicit and debuggable.

### 4.3 Reduce `_draw_card_row` parameter overload
Current function has too many parameters and mixed responsibilities.

Plan:
1. Identify stable data groupings.
2. Introduce one small dataclass if it removes obvious parameter noise.
3. Keep the dataclass concrete and local to card-row rendering.

Example direction:
- `CardRowRenderSpec` with label, cards, dimensions, bindings, selection metadata

Only do this if it clearly simplifies call sites. Otherwise prefer two smaller helper functions instead.

### 4.4 Extract session/setup orchestration helpers
Good candidates:
- session creation/restart logic
- map/deck/profile selection logic
- save/load adapter logic

Keep `GameViewerApp` focused on UI coordination rather than data assembly.

## Phase 5: State Model Follow-up

### 5.1 Leave `engine/state.py` mostly alone initially
This file is central and not the main complexity source.

Only consider changes if Phase 2 reveals repeated awkward model handling.

### 5.2 Add coverage around central state construction
Because `engine/state.py` is an untested hotspot, add tests around:
- `build_initial_game_state`
- `create_player_state`
- any state helpers touched indirectly by rule refactors

Avoid speculative model redesign.

## Execution Order
1. Add characterization tests for generic rule selection/action behavior.
2. Extract helpers from `_legal_generic_target_selection_moves`.
3. Run targeted engine tests.
4. Extract helpers from `_apply_generic_action`.
5. Remove tiny obvious duplication in rule helpers.
6. Run full engine-related tests.
7. Split `BoardCreatorApp._build_ui` and event routing.
8. Extract mode-specific board creator behavior.
9. Split `GameViewerApp._build_ui` and `_refresh_view`.
10. Reduce `_draw_card_row` complexity.
11. Run relevant test suite and any manual UI smoke checks.

## Validation Plan
- Run targeted pytest subsets after each engine step.
- Run broader pytest suite after `engine/rules.py` refactor.
- Run any existing UI-related tests.
- Perform manual smoke checks for:
  - board creator open/new/save/zoom/basic node edit
  - game viewer start game, inspect market/hand, basic move flow

## Success Criteria
- `engine/rules.py` no longer contains 400+ line and 600+ line brain methods.
- Generic selection and application logic are split by operation with readable names.
- `BoardCreatorApp` event handlers and UI setup are meaningfully smaller.
- `GameViewerApp` UI build and refresh paths are broken into understandable sections.
- No behavior regressions in engine tests.
- No new framework, registry, or abstraction layer is introduced without clear repeated need.

## Non-Goals
- No full rewrite of rules engine.
- No conversion to class-heavy architecture.
- No premature optimization of deep-copy semantics without evidence.
- No broad redesign of Pydantic models unless refactor uncovers a concrete bug or repeated pain point.

## Key Principle
Make one demon smaller at a time. Keep code working after every cut. Prefer obvious helper functions over big-brain architecture.
