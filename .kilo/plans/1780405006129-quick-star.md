# Plan: Split `_apply_generic_action` into per-op helpers

## Goal
Refactor `engine/rules.py` so `_apply_generic_action` no longer contains one giant `if action.op == ...` chain. Each supported `action.op` should move into a focused helper such as `_apply_generic_deploy_troops`, `_apply_generic_assassinate_troop`, and so on, while preserving behavior exactly.

## Why
- `_apply_generic_action` is about 794 lines and is the main complexity hotspot in `engine/rules.py`.
- The function mixes many unrelated behaviors, which makes debugging and future card additions risky.
- The engine already has strong integration coverage for generic-card behavior in `tests/test_generic_interpreter.py`, `tests/test_rules.py`, `tests/test_first_ten_cards.py`, and scenario tests. This makes small behavior-preserving extraction practical.

## Constraints
- Keep behavior identical.
- Keep refactor small and incremental.
- Do not change move payloads, state models, or public engine API.
- Prefer locality: keep the helper functions in `engine/rules.py` for now rather than splitting files in the same change.
- Avoid introducing registries or decorator dispatch for `action.op` in this refactor. Simple `if` dispatch at top level is acceptable if each branch immediately hands off to a focused helper.

## Observed Coverage To Lean On
- `tests/test_generic_interpreter.py` exercises many `generic_card` action ops directly with small custom cards.
- `tests/test_rules.py` exercises real catalog cards and multi-step pending generic choice flows.
- `tests/test_scenarios.py` covers persistence/restoration of `pending_generic_choice`.
- Existing tests already cover modal, repeat, deploy, assassinate, spy movement, return unit, devour, and many promotion paths.

## Refactor Shape

### 1. Add characterization tests before moving code
Add focused tests only where current coverage looks indirect or branch-heavy.

Suggested additions:
- `test_generic_gain_resource_adds_power`
- `test_generic_gain_resource_adds_influence`
- `test_generic_draw_cards_reshuffles_when_needed`
- `test_generic_grant_vp_uses_fixed_count`
- `test_generic_grant_vp_uses_scaled_count`
- `test_generic_recruit_card_rejects_invalid_market_slot_or_restriction`
- `test_generic_promote_top_of_deck_moves_top_card_to_inner_circle`
- `test_generic_play_card_from_market_applies_nested_effect_without_losing_outer_pending_context`
- One focused test per implemented `conditional_bonus` family if not already directly covered
- One focused test per implemented `custom_effect` family if not already directly covered

Testing style:
- One behavior per test.
- Keep helper builders already used in `tests/test_generic_interpreter.py`.
- Prefer direct asserts on state deltas, not snapshots of whole state.

### 2. Extract lowest-risk helpers first
Start with branches that are self-contained and have minimal cross-branch interaction.

Recommended first extractions:
- `_apply_generic_gain_resource`
- `_apply_generic_draw_cards`
- `_apply_generic_grant_vp`
- `_apply_generic_devour`

Each helper should accept the same common shape:
- `state: GameState`
- `player_id: str`
- `card: CardDefinition`
- `source_card_id: str`
- `action: CardAction`
- `selection: dict[str, object]`

Even if some parameters are unused, keeping one shared signature makes extraction simple and avoids clever branching signatures.

After each extraction:
- Run targeted tests for generic interpreter and rules.
- Only continue if green.

### 3. Extract board-targeting action helpers next
Move medium-complexity ops into separate helpers:
- `_apply_generic_deploy_troops`
- `_apply_generic_assassinate_troop`
- `_apply_generic_supplant_troop`
- `_apply_generic_place_spy`
- `_apply_generic_return_spy`
- `_apply_generic_return_unit`
- `_apply_generic_move_troop`

Notes:
- Preserve existing use of `_apply_free_deploy`, `_apply_free_assassinate`, and `_apply_return_spy`.
- Keep existing counter updates on `pending_generic_choice.action_counters` exactly where they are today.
- Do not unify troop/spy movement logic in this pass.

### 4. Extract card-zone and promotion helpers after board helpers
These are trickier because they interact with pending state and nested effect resolution.

Extract:
- `_apply_generic_promote_card`
- `_apply_generic_recruit_card`
- `_apply_generic_play_card`

Notes:
- `_apply_generic_promote_card` is the highest-risk extraction because it contains several sub-modes:
  - top-of-deck promotion
  - multiple-zone promotion
  - discard promotion
  - threshold self-promotion
  - selected played-card promotion
  - deferred end-of-turn promotion queueing
- Keep the internal sub-branches inside this helper for now. The first win is moving the logic out of the monolith.
- `_apply_generic_play_card` must preserve the current outer pending choice behavior and current explicit errors for unsupported nested prompts.

### 5. Extract rule-special helpers last
These branches are broad and metadata-heavy.

Extract:
- `_apply_generic_conditional_bonus`
- `_apply_generic_custom_effect`

Notes:
- Keep each condition/effect kind as plain `if` branches inside its helper for now.
- This refactor should reduce one giant switch into a few smaller switches, not attempt a grand redesign.

### 6. Reduce `_apply_generic_action` to thin dispatcher
After extractions, `_apply_generic_action` should look like:
- resolve count and normalize selection
- keep the early `_action_focus_requirement_met` guard
- dispatch by `action.op` to one helper per op
- raise the existing `MissingRuleImplementationError` for unknown ops

This is a good end state for this change even if dispatch still uses `if` statements.

## Verification Plan
Run in stages, not only at end.

Suggested sequence:
1. `pytest -q tests/test_generic_interpreter.py`
2. `pytest -q tests/test_rules.py -k generic`
3. `pytest -q tests/test_first_ten_cards.py`
4. `pytest -q tests/test_scenarios.py -k pending_generic_choice`
5. If all above pass, run broader engine confidence suite:
   - `pytest -q tests/test_rules.py tests/test_generic_interpreter.py tests/test_first_ten_cards.py tests/test_scenarios.py tests/test_state_machine.py`

## Implementation Notes
- Keep helper names private and explicit.
- Place extracted helpers near `_apply_generic_action` so readers do not jump around the file too much.
- Avoid new abstractions like handler dicts, base classes, or protocol layers.
- Preserve exact exception types and messages where practical, since tests may assert on them.
- Preserve deep-copy vs in-place behavior exactly. Many branches currently rely on careful `model_copy(deep=True)` placement.
- Preserve existing local helper use like `_require_selection_string`, `_require_selection_int`, `_apply_devour_once`, `_threshold_self_promote_enabled`, and `_promote_*` helpers.

## Risk List
- Changing copy boundaries could mutate shared pending state unexpectedly.
- Promotion logic has many modes and deferred queue interactions.
- Nested `play_card` logic temporarily clears and restores `pending_generic_choice`; easy place for regression.
- Some behavior is covered only indirectly by real card tests, so targeted characterization tests are important before moving the riskiest branches.

## Recommended Execution Order
1. Add missing characterization tests.
2. Extract simple resource/card-count branches.
3. Extract board-targeting branches.
4. Extract promotion/recruit/play-card branches.
5. Extract `conditional_bonus` and `custom_effect`.
6. Run broader verification suite.

## Definition Of Done
- `_apply_generic_action` is a short dispatcher instead of a 794-line monolith.
- Existing generic-card behavior remains unchanged.
- Added tests cover the most branch-heavy or indirectly covered helper paths.
- Targeted pytest suites pass.
