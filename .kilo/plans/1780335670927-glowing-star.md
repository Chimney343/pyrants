# Plan: Shared Board Viewing Interface

## Goal
Create a shared board viewing layer used by both `interface/board_creator.py` and `interface/game_viewer.py`, while preserving the current responsibilities:
- `board_creator` can mutate topology and layout during editing.
- `game_viewer` treats the board package as static and only overlays engine/game state.

## Success Criteria
1. One shared geometry/rendering path draws board edges, site shapes, route shapes, labels, and common scaling behavior for both tools.
2. `board_creator` still supports editor-only visuals such as selection, connect anchors, pending connect overlays, grid, and background image.
3. `game_viewer` still supports gameplay-only visuals such as troop occupancy, spies, control markers, and highlight state.
4. Existing renderer behavior remains covered by tests, with new tests proving the shared layer is used by both tools.
5. No engine coupling is introduced into the board creator, and no editor mutation state leaks into the game viewer.

## Current Findings

### Existing split
- `interface/board_renderer.py` draws editor geometry directly from `BoardCreatorApp` state.
- `interface/game_renderer.py` separately rebuilds nearly the same board geometry from `BoardPackageDefinition` layout + topology.
- Both renderers independently:
  - traverse adjacency to draw edges
  - branch on `NodeKind.SITE` vs `NodeKind.ROUTE`
  - draw site rectangles and route circles
  - place labels
  - scale coordinates and widths
- `game_renderer.py` defines its own `LayoutNodeView` to merge board and layout data.
- `board_creator.py` defines its own `EditableNode` to merge mutable board and layout data.

### Important differences that should remain separate
- Editor-only concerns:
  - grid drawing
  - background image
  - selected node outline
  - connect-start outline
  - pending connect overlay line
  - direct access to mutable `EditableNode` structures
- Game-viewer-only concerns:
  - occupancy coloring
  - troop token fills
  - spy labels
  - control/VP text
  - dependence on `GameView`

### Architectural implication
The duplication is in the common board geometry/view layer, not in the app-specific overlays. The safest refactor is to extract:
- a shared node/edge projection model
- a shared base renderer for board geometry
and keep editor/game overlays in thin specialized renderers.

## Recommended Design

### 1. Introduce a shared board view model module
Add a new interface-level module, tentatively `interface/board_view.py`, containing immutable shared projection types and helpers.

Suggested contents:
- `BoardNodeView`
  - `node_id`
  - `label`
  - `kind`
  - `center_x`
  - `center_y`
  - `bounds`
  - `troop_slot_points`
  - `adjacent_to`
- `BoardEdgeView`
  - `start_node_id`
  - `end_node_id`
  - optionally resolved endpoints if that makes rendering simpler
- helper constructors:
  - `build_board_node_views_from_package(package: BoardPackageDefinition) -> dict[str, BoardNodeView]`
  - `build_board_node_views_from_editor(nodes: dict[str, EditableNode], node_order: list[str]) -> dict[str, BoardNodeView]`
  - `build_board_edges(node_views: dict[str, BoardNodeView], node_order: Sequence[str] | None = None) -> tuple[BoardEdgeView, ...]`

Why this shape:
- `BoardPackageDefinition` stays the read-only source for game viewing.
- `EditableNode` stays the mutable source for editing.
- Both are projected into the same render-ready shape.
- Shared code stops depending on app classes.

### 2. Introduce a shared base canvas renderer
Add a new module, tentatively `interface/shared_board_renderer.py`, responsible only for common geometry drawing.

Suggested responsibilities:
- clear canvas if requested
- draw shared edges
- draw site base geometry
- draw route base geometry
- draw shared labels
- centralize scale math and common constants such as route radius, edge width, fonts, label offsets

Suggested API shape:
- `SharedBoardRenderer.redraw(canvas, node_views, *, scale=1.0, node_order=None, style_resolver=None, overlay_renderer=None)`

Simpler alternative, likely better for this repo:
- keep it concrete and avoid callback-heavy abstraction.
- Provide methods like:
  - `draw_edges(...)`
  - `draw_site_base(...)`
  - `draw_route_base(...)`
  - `draw_label(...)`
- Then let thin wrappers call these methods in a fixed sequence.

Recommendation:
Prefer the simpler concrete base-class design over a highly generic callback API. It is easier to test and matches the repo’s preference for small, direct abstractions.

### 3. Refactor `BoardRenderer` into an editor-specific wrapper
Keep `interface/board_renderer.py`, but reduce it to editor-only behavior layered on top of shared geometry.

Planned responsibilities after refactor:
- still accept the app object to minimize churn in `board_creator.py`
- still draw:
  - background image
  - grid
  - editor-specific node outlines/colors
  - editor troop slot placeholders
  - pending connect overlay
- stop owning edge traversal and base shape math directly when that logic can be shared

Likely implementation approach:
- convert editor app state into shared `BoardNodeView` values via helper
- reuse shared edge drawing and common node placement logic
- keep editor-only styles in `board_renderer.py`

### 4. Refactor `GameBoardRenderer` into a gameplay-specific wrapper
Keep `interface/game_renderer.py`, but make it consume the shared node projection and base drawing behavior.

Planned responsibilities after refactor:
- build shared `BoardNodeView` values from `BoardPackageDefinition`
- add gameplay-only overlays:
  - troop occupancy
  - route ownership fill
  - spy labels
  - owner/VP text
  - highlight state
- stop owning its own duplicate `LayoutNodeView` unless that exact class becomes the shared `BoardNodeView`

Recommendation:
Delete `LayoutNodeView` in favor of the new shared view model once tests are migrated.

### 5. Keep mutation and static consumption separate at the boundary
This is the core design rule for avoiding future drift.

Boundary rule:
- `board_creator` mutates `EditableNode` and related app/editor state.
- `game_viewer` consumes `BoardPackageDefinition` and `GameView` only.
- Shared renderer modules consume only render-ready projection objects (`BoardNodeView`) plus optional style/overlay inputs.

That gives one shared viewing interface without forcing either side into the other side’s data model.

   Verify: behavior unchanged; optional micro-optimization only if the code stays simple.

## Tradeoffs

### Recommended approach: shared geometry + specialized overlays
Pros:
- minimal architectural change
- preserves app boundaries
- directly addresses the drift problem
- easy to test
- avoids pushing editor state into gameplay code

Cons:
- still leaves two thin renderer entry points
- some style differences will remain intentionally duplicated

### Alternative: single universal renderer with mode flags
Example: one renderer class with `mode="editor" | "game"`.

Pros:
- one top-level renderer

Cons:
- mixes unrelated responsibilities
- tends to grow conditionals quickly
- makes mutation/static boundaries less clear
- more fragile over time

Recommendation:
Do not use a single mode-switched renderer. Use a shared base/view-model layer plus two thin adapters.

## Assumptions
- The user wants a plan for a maintainable shared rendering architecture, not a one-off sync of current visuals.
- Matching exact current pixel output is desirable but not more important than removing duplicate geometry logic.
- It is acceptable to add one or two new interface modules if they reduce duplication cleanly.

## Open Decision For Implementation
One small design choice remains:
- Option A: shared helper functions + thin composition in each renderer
- Option B: shared base class that both renderers subclass

Recommendation: Option A.
Reason: this codebase is currently straightforward and function-oriented in the rendering layer; composition keeps the abstraction smaller and easier to test than inheritance.

## Execution Notes
- Keep changes surgical: no board-creator behavior changes beyond consuming the shared geometry layer.
- Do not change engine/state or package schemas unless implementation exposes a real gap.
- Remove only duplication made obsolete by the refactor; do not broaden cleanup.
