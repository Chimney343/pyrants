# Refactor plan for `game_setup/state_generator.py`

## Goal
Split `game_setup/state_generator.py` by responsibility, create a dedicated scenario-generation package, and add a narrow `CardScenarioGenerator` class after the split.

## Requested direction
User explicitly chose:
1. Split module as intended.
2. Create a separate folder just for scenario generation.
3. Add `CardScenarioGenerator` after the split.

This removes earlier open tradeoff. Plan below assumes implementation should proceed in that direction.

## What grug found

### 1. File has two distinct jobs
`game_setup/state_generator.py` currently mixes two related but different responsibilities:

1. Generic random-state search helpers:
- `_fresh_initial_state`
- `find_state`
- `find_state_and_save`
- `generate_states`
- simple predicate builders like `has_card_in_hand`

2. Card-scenario generation pipeline:
- `iter_roster_card_ids`
- `_build_card_scenario_setup`
- `_search_card_scenario`
- `find_card_scenario`
- `ensure_card_scenario`
- `write_forced_injection_notes`
- `generate_card_scenarios`

### 2. Current import surface is small and manageable
Direct imports of `game_setup.state_generator` currently appear in:
- `tests/test_state_generator.py`
- `scripts/generate_card_scenarios.py`
- `game_setup/__init__.py`

This is good news. Blast radius small. grug can preserve compatibility while moving code.

### 3. Current design is function-first, mostly stateless
Most functions are orchestration around:
- file paths
- seeds / RNG creation
- engine rules (`legal_moves`, `apply`, `is_terminal`)
- scenario persistence

This means a giant all-purpose class still bad idea. But a small class for scenario workflow is now justified because user explicitly wants it and because that half of module repeats same configuration many times.

## Walkthrough summary

### Generic search side
- `_base_state_paths()` and `_fresh_initial_state(...)` create initial states.
- `find_state(...)` performs deterministic random walk until predicate matches.
- `find_state_and_save(...)` persists one found state.
- `generate_states(...)` creates many independent walked states.
- predicate helpers return tiny closures.

This side should stay function-based.

### Scenario-generation side
- `iter_roster_card_ids(...)` collects deterministic target ids.
- `_build_card_scenario_setup(...)` assembles synthetic setup with roster coverage.
- `_search_card_scenario(...)` tries repeated biased random walks.
- `find_card_scenario(...)` returns only truly reachable state.
- `ensure_card_scenario(...)` force-injects on failure.
- `generate_card_scenarios(...)` saves fixtures and notes.

This side has real shared config and is reasonable home for a small class.

## Target design

### 3. Add narrow `CardScenarioGenerator` class
Create a small config-owning class in `game_setup/scenario_generation/card_scenarios.py`.

Recommended shape:

```python
@dataclass(frozen=True)
class CardScenarioGenerator:
    board_path: Path = DEFAULT_BOARD_PATH
    card_path: Path = DEFAULT_CARD_PATH
    setup_path: Path = DEFAULT_SETUP_PATH
    rosters_path: Path = DEFAULT_ROSTERS_PATH
    player_ids: tuple[str, ...] = ("p1", "p2", "p3", "p4")
    base_seed: int = 0
    max_attempts: int = 20
    max_steps_per_attempt: int = 1000

    def find(self, target_card_id: str, *, verbose: bool = False) -> GameState | None: ...
    def ensure(self, target_card_id: str, *, verbose: bool = False) -> tuple[GameState, dict[str, object] | None]: ...
    def generate(
        self,
        output_dir: Path,
        *,
        card_ids: list[str] | None = None,
        verbose: bool = True,
    ) -> tuple[list[Path], list[str]]: ...
    def iter_card_ids(self) -> list[str]: ...
```

Notes:
- Keep class narrow. no inheritance, no strategy pattern, no abstract nonsense.
- Store `player_ids` as tuple on instance to avoid mutable default trouble.
- Instance methods should delegate to existing internal helpers after split.
- `generate(...)` should derive per-card seeds same way current function does.

### 4. Preserve top-level compatibility API
Keep `game_setup/state_generator.py`, but shrink it into thin compatibility re-export module.

It should re-export:
- generic search functions from `random_state_search.py`
- scenario functions/constants/class from `scenario_generation.card_scenarios`

Reason:
- existing imports keep working
- script/tests can be migrated gradually
- lower refactor risk

### 5. Update package exports cleanly
Update `game_setup/__init__.py` to import from new modules, not from old mixed implementation.

Expose:
- generic search helpers
- scenario-generation functions
- `CardScenarioGenerator`

Potentially also expose scenario-generation package symbols from `game_setup/scenario_generation/__init__.py` for clean imports.

## Class introduction strategy
Add class after code split, not before.

Suggested order:
1. Copy/move scenario functions into `scenario_generation/card_scenarios.py`.
2. Make old public functions call same logic from new location.
3. Add `CardScenarioGenerator` as thin wrapper around those moved helpers.
4. Optionally update script to use the class directly.

This keeps each step small and easy to verify.

## Risks and how to avoid them

### Risk 1: circular imports
Avoid by:
- keeping scenario package independent of `game_setup.__init__`
- importing concrete helpers directly from `game_setup.loaders` and `game_setup.scenarios`
- making compatibility module only re-export, not add logic

### Risk 2: mutable config defaults in class
Avoid by:
- using tuple for `player_ids`
- converting to list only when calling lower-level helpers if needed

### Risk 3: behavior drift during move
Avoid by:
- move code with minimal edits first
- preserve helper function bodies where possible
- add class as wrapper rather than rewriting search internals

### Risk 4: too much package fragmentation
Avoid by:
- one new package with one main module initially
- do not create many micro-modules yet

## Final recommendation
Implement this as:
1. `random_state_search.py` for generic search functions.
2. `scenario_generation/` package for card scenario workflow.
3. narrow `CardScenarioGenerator` class inside scenario-generation module.
4. `state_generator.py` kept as compatibility shim.

This satisfies user request while keeping complexity demon trapped in one crystal instead of letting spirit roam whole cave.
