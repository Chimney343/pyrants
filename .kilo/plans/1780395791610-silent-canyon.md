# Plan: 125 Reachable Card Scenarios

## Confirmed Requirements

The generator must produce **125 scenario JSON files** with these exact properties:

1. Every scenario uses `data/boards/tyrants_of_the_underdark.json`.
2. Viewer compatibility should come from the existing matching layout file: `data/layouts/tyrants_of_the_underdark_layout.json`.
3. Every scenario has **4 players**.
4. Every scenario is a **reachable** state obtained by applying legal moves from a proper initial game state.
5. Every scenario is **non-terminal** and in **main phase**.
6. In every scenario, the **current player** has the dedicated target card in hand.
7. That target card is not just present - it must be **immediately playable**, meaning a legal `PlayCardMove` exists for that exact card.
8. One scenario is generated for each of the **125 unique card ids**.

## Current Code State

Relevant existing pieces:

- `game_setup/scenarios.py` already saves and loads validated scenario JSON.
- `game_setup/state_generator.py` already does bounded random rollouts, but it is hard-coded to:
  - `base_game.json`
  - `base_setup.json`
  - default 2-player usage in tests
  - generic predicates only
- `scripts/check_roster_card_stuck_states.py` already:
  - enumerates 125 unique card ids from `first_deck_rosters.json`
  - proves the repo already has a deterministic 125-card iteration path
  - but it **injects** target cards into hand, so it does **not** satisfy the reachable-rollout requirement
- `first_deck_rosters.json` covers **all 125 unique cards**.
- `base_setup.json` is too small for this task by itself, because its market only contains `priestess_of_lolth`.

## Key Design Decision

The generator should **not** use the current stuck-state probe approach of directly placing the target card into hand.

Reason:

- You explicitly required a state reached through legal rollout only.
- Injecting cards into hand is useful for coverage probes, but it violates the stricter interpretation of "legal" you chose.

## Recommended Design

Use a dedicated **card-scenario generator script** backed by a few small state-generator helpers.

### 1. Build a full-coverage initial setup

Create a generator-specific setup payload in code:

- starter deck: reuse the standard starter deck from `base_setup.json`
- market deck: combine all roster decks whose cards should enter the normal market
- market row size: reuse `base_setup.json`
- board: `tyrants_of_the_underdark.json`
- players: `p1`, `p2`, `p3`, `p4`

Important note:

- `first_deck_rosters.json` contains 10 deck entries, including starter and special recruit stacks.
- The generator should use roster data as the card source of truth, but it should **not** blindly dump every roster entry into the market deck.
- The special recruit cards (`house_guard`, `priestess_of_lolth`, `insane_outcast`) already have dedicated engine support through fixed recruit slots.
- The simplest correct setup is:
  - starter deck from base setup
  - market deck from the normal roster market decks
  - keep special recruit cards handled by engine rules rather than duplicating them into the market unless testing proves duplication is required

## 2. Add a dedicated single-card search function

Add a helper that searches for one card-specific scenario:

- input:
  - `target_card_id`
  - `board_path`
  - `card_path`
  - `rosters_path`
  - `base_setup_path`
  - `seed`
  - `max_steps_per_attempt`
  - `max_attempts`
- behavior:
  - build the 4-player full-coverage initial state
  - run a bounded random legal rollout
  - accept the first state that matches all requirements
- acceptance predicate:
  - `state.definition.board.board_id == "Tyrants of the Underdark"`
  - `len(state.turn_order) == 4`
  - `state.phase == TurnPhase.MAIN`
  - `not is_terminal(state)`
  - `target_card_id in state.players[state.current_player_id].hand`
  - there exists a legal `PlayCardMove` for `target_card_id`

This should return `GameState | None`.

## 3. Keep the rollout random, but allow search retries

A single uniform random rollout is unlikely to find all 125 cards reliably.

Use this shape:

- For each target card, try multiple deterministic attempts.
- Each attempt starts from a fresh legal 4-player initial state.
- Each attempt uses a deterministic seed derived from:
  - base seed
  - card index
  - attempt index
- Within an attempt, moves are still chosen randomly from legal moves.

Recommended initial strategy:

- start with **uniform random legal move selection**
- only add weighted target-aware move bias if coverage is poor in practice

Reason:

- This keeps the first implementation simple.
- It respects your requirement for random reachable states.
- It avoids prematurely building a complex move-chooser system.

## 4. Add batch generation for all 125 cards

Add a batch generator that:

- gets the 125 unique card ids in deterministic order
- runs the single-card search for each card
- saves one scenario file per successful hit
- fails clearly if any card cannot be generated within budget

Recommended output naming:

- `data/scenarios/cards/001_aboleth.json`
- `data/scenarios/cards/002_advance_scout.json`
- ...

Recommended metadata per file:

- `scenario_id`: stable file-stem id
- `description`: include board, 4-player, reachable-rollout wording
- `tags`: `generated`, `cards`, `reachable`, `playable_now`
- `card_under_test`: target card id

## 5. Do not over-generalize the existing generator

Keep changes surgical.

Recommended split:

- `game_setup/state_generator.py`
  - extend with card-targeted reachable search helpers
- `scripts/generate_card_scenarios.py`
  - CLI entry point that generates one or all scenarios
- `tests/`
  - add focused tests for builder, predicate, and small-batch generation

Avoid:

- refactoring unrelated generator code
- moving existing probe script logic unless necessary
- inventing a general-purpose move strategy framework

## Success Criteria

The implementation is done when all of these are true:

1. A generator command can produce scenario files on disk for a chosen card subset.
2. A full run can produce **125 scenario files**.
3. Every saved scenario reloads through `load_game_state_from_scenario`.
4. Every saved scenario:
   - uses the Tyrants board
   - has 4 players
   - is in main phase
   - is non-terminal
   - has the dedicated card in the current player's hand
   - has a legal `PlayCardMove` for that card
5. CI tests cover the builder and subset generation path without requiring the full 125-card run.

## Risks and Mitigations

### Risk 1: pure uniform rollouts do not find all 125 cards within budget

Mitigation:

- implement deterministic retries per card first
- if coverage is still poor, add a **small weighted chooser** that still picks randomly but slightly favors:
  - recruit moves
  - card draw progress
  - progression through turns

Do **not** jump to this unless the simpler version demonstrably fails.

### Risk 2: special recruit cards are unreachable under the first market setup

Mitigation:

- verify `house_guard`, `priestess_of_lolth`, and `insane_outcast` early with targeted smoke tests
- if one of them is missing, adjust the setup builder or search budget specifically for that path

### Risk 3: full 125-card generation is slow

Mitigation:

- keep full generation out of pytest
- make the CLI support one-card and subset runs for debugging
- keep the seed schedule deterministic so failures are reproducible

## Recommended Execution Order

1. Add full-coverage setup builder for Tyrants + 4 players
   - verify: initial state builds correctly and roster coverage is available
2. Add single-card playable-now predicate and search
   - verify: one easy card scenario can be found and reloaded
3. Add batch generator CLI
   - verify: 2-3 deterministic cards generate and save correctly
4. Run full 125-card generation manually
   - verify: 125 files created, zero missing cards
5. Tighten search only if coverage gaps appear
   - verify: previously missing cards now generate without changing acceptance rules

## Final Recommendation

Implement a **dedicated reachable-rollout card scenario generator**, not a general scenario framework extension and not a hand-injection tool.

The minimal correct approach is:

- build one full-coverage 4-player Tyrants setup
- search one target card at a time via repeated deterministic random rollouts
- accept only non-terminal main-phase states where that card is currently playable
- save one JSON scenario per unique card id

That matches your constraints directly and avoids speculative abstractions.
