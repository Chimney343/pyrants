# Re-Review: /engine (post-helpers extraction)

## What changed since first review

| Before | After |
|--------|-------|
| `rules.py` + `generic_runtime.py` circular-dep via `_get_rules()` lazy import | Clean DAG: `helpers` ← `rules`, `helpers` ← `generic_runtime` |
| `rules.py` 1202 lines | `rules.py` 666 lines (-45%) |
| `_apply_generic_action` 55-line if/elif | 6-line dict dispatch (`_GENERIC_ACTION_APPLIERS`, 17 handlers) |
| `_apply_generic_custom_effect` 122-line if/elif | 6-line dict dispatch (`_CUSTOM_EFFECT_HANDLERS`, 7 single-responsibility handlers) |
| — | `helpers.py` created (604 lines, shared utilities with clear section headers) |

## What grug praise (shiny rocks)

- **Circular dependency dead.** Import graph clean. Each module independent.
- **Dict dispatch pattern applied consistently.** Adding new `action.op` now means: write one handler function, add one line to dict. No more editing a giant chain.
- **Custom effect handlers extracted.** Each one named, individually testable. `_custom_effect_scaled_resource_from_player_zone`, `_custom_effect_give_insane_outcast_to_each_opponent`, etc. Single responsibility.
- **`rules.py` size halved.** Public API, move handlers, phase transitions — all visible in 666 lines without scrolling through 30 shared utility functions.
- **`phases.py` (55 lines), `scoring.py` (94 lines), `errors.py` (17 lines), `moves.py` (153 lines)** — all small, focused, clean. Perfect grug modules.
- **`state.py`** — frozen Pydantic models, clear domain separation, immutability enforced at type level.

## What grug still worry about (complexity demon not fully trapped)

### 1. `generic_runtime.py` still 2281 lines

Why bigger than before (2125)? custom-effect handlers got 6-parameter function signatures. But the real problem is `_legal_generic_target_selection_moves` (~500 lines, lines 394-893), which is a giant if/elif chain dispatching by `action.op`. This is the same anti-pattern we fixed in `_apply_generic_action`.

**Suggestion:** Mirror the dict-dispatch pattern. Create `_LEGAL_TARGET_HANDLERS` dict mapping `action.op` → function. Each handler is a small function that returns `list[Move]`. This splits the 500-line monster into ~14 focused functions.

### 2. `_legal_generic_target_selection_moves` has a nested `_append_for_zone` closure

Lines 834-883 define `_append_for_zone` inside the function body. This is hard to test in isolation. Dict dispatch would eliminate the closure.

### 3. `_apply_generic_conditional_bonus` still if/elif (5 conditions)

Lines 1804-1958 (needs verification). Five conditions with nearly identical "check condition → grant resource" structure. Each one duplicates 20+ lines of resource-granting boilerplate.

**Suggestion:** Extract a `_grant_resource(state, player_id, resource, amount)` helper. Then each condition becomes: check → call `_grant_resource`. Reduces ~150 lines to ~60.

### 4. `_scaled_vp_award_count` silent fallback to 0

`helpers.py:264-265`: `else: return 0`. When a new `count_from` is added to card data but not handled here, VP silently becomes 0 instead of raising a clear error.

**Suggestion:** Raise `MissingRuleImplementationError` for unrecognized `count_from` values.

### 5. `_auto_resolve_pending_generic` silently skips actions

Lines 1022-1026: when `_action_requires_selection` returns True but `selectable_moves` is empty, the action is silently skipped (`pending.next_action_index += 1; continue`). No log, no trace, no way to debug why a card didn't fire.

**Suggestion:** At minimum, collect skipped action_ids and return them in a debug attribute. Or log at debug level.

### 6. Duplicated draw logic across modules

- `state.py:draw_cards()` — shuffles via `rng.shuffle()`
- `generic_runtime.py:_apply_generic_draw_cards()` — shuffles via `_reshuffle_discard_into_deck()`
- `rules.py:_apply_cleanup()` — inline draw-5 logic

Three places, same concept. Not yet enough for abstraction (Rule of Three says 3 is the threshold), but the differences (seeded shuffle vs rng shuffle) are subtle and error-prone.

### 7. `_count_controlled_sites` and `_count_controlled_sites_by_troops` nearly identical

`helpers.py:110-127` and `130-147`. Only difference: `_count_controlled_sites` checks `has_presence`, `_count_controlled_sites_by_troops` checks troop majority. Both ~18 lines, almost identical structure.

**Suggestion:** If a third counting variant appears, extract the shared loop. For now, keep both — duplication is simpler than wrong abstraction.

### 8. `_legal_main_phase_actions` dead code

`rules.py:318`: `board_definitions = board_index(state.definition.board)` — computed but never read. Remove.

### 9. `_apply_effect_with_wrappers` returns mutated object

`helpers.py:305-328`: calls `effect(updated, player_id, card)` where `effect` may mutate state directly (e.g., `_effect_gain_power` does `updated.resource_pool.power += ...` which mutates `updated` in place, but it also does `state.model_copy(deep=True)` so it's a new object). The function contract says "return a new state" but the effect functions mutate `updated` directly. This is fine in practice (immutable output) but the function name `_apply_effect_with_wrappers` doesn't clearly signal it creates its own copy.

**Verdict:** Not broken, but the mutation-vs-copy boundary is unclear. Low priority.
